# FreshLoop — Database Architecture & Schema Documentation
**Team**: HexaCore  
**System**: FreshLoop Surplus Food Matching  
**Core Maxim**: *“A suggested match is not a completed donation. Only the quantity confirmed as collected can contribute to verified impact metrics.”*

---

## 1. Schema Overview

The database is built on PostgreSQL with strict relational integrity, foreign key cascades, check constraints, and Row Level Security (RLS) policies.

```
       ┌──────────────────────┐
       │    organisations     │
       └──────────┬───────────┘
                  │
      ┌───────────┴───────────┬──────────────────────┐
      ▼                       ▼                      ▼
┌──────────────┐    ┌─────────────────────┐   ┌───────────────┐
│   profiles   │    │  surplus_listings   │   │ kitchen_reqs  │
└──────────────┘    └──────────┬──────────┘   └───────┬───────┘
                               │                      │
                               └──────────┬───────────┘
                                          ▼
                                   ┌──────────────┐
                                   │   matches    │
                                   └──────┬───────┘
                                          ▼
                                   ┌──────────────┐
                                   │ collections  │
                                   └──────┬───────┘
                                          ▼
                                   ┌──────────────┐
                                   │  audit_logs  │
                                   └──────────────┘
```

## 2. Table Definitions

### 2.1 `organisations`
Stores participating commercial food donors (vendors) and recipient community kitchens/shelters.
- `id` (UUID, PK)
- `name` (TEXT, NOT NULL)
- `type` (TEXT, CHECK: `'vendor' | 'kitchen' | 'admin'`)
- `contact_name` (TEXT, NOT NULL)
- `contact_email` (TEXT, NOT NULL)
- `phone` (TEXT)
- `address` (TEXT, NOT NULL)
- `service_area` (TEXT)
- `lat` (DOUBLE PRECISION)
- `lng` (DOUBLE PRECISION)
- `operating_hours` (TEXT)
- `verified_status` (TEXT, CHECK: `'pending' | 'verified' | 'rejected'`)
- `created_at`, `updated_at` (TIMESTAMPTZ)

### 2.2 `profiles`
Links Supabase authenticated accounts (`auth.users`) to organisational roles.
- `id` (UUID, PK, FK to `auth.users.id`)
- `organisation_id` (UUID, FK to `organisations.id`)
- `full_name` (TEXT, NOT NULL)
- `email` (TEXT, NOT NULL)
- `role` (TEXT, CHECK: `'vendor' | 'kitchen' | 'admin'`)
- `created_at`, `updated_at` (TIMESTAMPTZ)

### 2.3 `surplus_listings`
Manages surplus food posted by verified vendors.
- `id` (UUID, PK)
- `vendor_org_id` (UUID, FK to `organisations.id`)
- `title` (TEXT, NOT NULL)
- `food_category` (TEXT, CHECK: `'vegetables' | 'fruit' | 'bakery' | 'packaged_food' | 'prepared_food' | 'dairy' | 'beverages' | 'other'`)
- `description` (TEXT)
- `total_quantity` (NUMERIC(10,2), CHECK > 0)
- `available_quantity` (NUMERIC(10,2), CHECK >= 0)
- `reserved_quantity` (NUMERIC(10,2), DEFAULT 0, CHECK >= 0)
- `collected_quantity` (NUMERIC(10,2), DEFAULT 0, CHECK >= 0)
- `unit` (TEXT, CHECK: `'kg' | 'meals' | 'boxes' | 'litres' | 'portions' | 'units'`)
- `prepared_at` (TIMESTAMPTZ)
- `expires_at` (TIMESTAMPTZ, NOT NULL)
- `pickup_start`, `pickup_end` (TIMESTAMPTZ, CHECK: `pickup_start <= pickup_end`)
- `pickup_address` (TEXT, NOT NULL)
- `storage_notes`, `allergens` (TEXT)
- `status` (TEXT, CHECK: `'draft' | 'available' | 'matched' | 'accepted' | 'partially_collected' | 'collected' | 'expired' | 'cancelled'`)
- **Invariant**: `available_quantity + reserved_quantity + collected_quantity = total_quantity`

### 2.4 `kitchen_requirements`
Demand specifications posted by community kitchens.
- `id` (UUID, PK)
- `kitchen_org_id` (UUID, FK to `organisations.id`)
- `accepted_categories` (TEXT[], NOT NULL)
- `desired_quantity` (NUMERIC(10,2), CHECK > 0)
- `min_quantity` (NUMERIC(10,2), CHECK > 0)
- `max_quantity` (NUMERIC(10,2), CHECK >= `min_quantity`)
- `unit` (TEXT, NOT NULL)
- `needed_by` (TIMESTAMPTZ, NOT NULL)
- `pickup_start`, `pickup_end` (TIMESTAMPTZ)
- `service_area` (TEXT)
- `storage_capabilities` (TEXT)
- `handling_restrictions` (TEXT)
- `is_active` (BOOLEAN, DEFAULT true)

### 2.5 `matches`
Persisted recommendations generated by the deterministic server matching engine.
- `id` (UUID, PK)
- `listing_id` (UUID, FK to `surplus_listings.id`)
- `requirement_id` (UUID, FK to `kitchen_requirements.id`)
- `vendor_org_id`, `kitchen_org_id` (UUID, FKs)
- `overall_score` (INTEGER, 0 to 100)
- `location_score` (INTEGER, 0-30)
- `quantity_score` (INTEGER, 0-25)
- `time_score` (INTEGER, 0-25)
- `demand_score` (INTEGER, 0-20)
- `explanations` (JSONB array of strings)
- `warnings` (JSONB array of strings)
- `status` (TEXT, CHECK: `'suggested' | 'accepted' | 'declined' | 'superseded'`)
- **Constraint**: `UNIQUE(listing_id, requirement_id)`

### 2.6 `collections`
The physical handover agreement and two-party verification record.
- `id` (UUID, PK)
- `listing_id` (UUID, FK)
- `match_id` (UUID, FK)
- `vendor_org_id`, `kitchen_org_id` (UUID, FKs)
- `accepted_quantity` (NUMERIC(10,2), CHECK > 0)
- `collected_quantity` (NUMERIC(10,2), NULL until collection recorded)
- `unit` (TEXT)
- `pickup_deadline` (TIMESTAMPTZ)
- `accepted_at`, `collected_at` (TIMESTAMPTZ)
- `vendor_confirmed` (BOOLEAN, DEFAULT false)
- `kitchen_confirmed` (BOOLEAN, DEFAULT false)
- `status` (TEXT, CHECK: `'pending_pickup' | 'collected_pending_confirmation' | 'confirmed' | 'disputed' | 'cancelled'`)
- `cancellation_reason`, `dispute_reason` (TEXT)

### 2.7 `audit_logs`
Tracks immutable state transitions, dispute logs, and admin moderations.

## 3. Row Level Security (RLS) Policy Matrix

| Table | Operation | Policy Rule |
| :--- | :--- | :--- |
| `organisations` | SELECT | Verified orgs are readable; users read own; admin reads all |
| `organisations` | ALL | Admin role only |
| `profiles` | SELECT | User reads own profile; admin reads all |
| `profiles` | UPDATE | User updates own profile only |
| `surplus_listings` | SELECT | Non-draft readable by all authenticated; drafts readable by owner or admin |
| `surplus_listings` | INSERT/UPDATE/DELETE | Vendor org owner only, or admin |
| `kitchen_requirements` | SELECT | Active requirements readable by all authenticated |
| `kitchen_requirements` | ALL | Kitchen org owner only, or admin |
| `matches` | SELECT/UPDATE | Only parties involved (`vendor_org_id` or `kitchen_org_id`) or admin |
| `collections` | SELECT/UPDATE | Only parties involved or admin |
| `audit_logs` | SELECT | Admin only |

## 4. Concurrency & Overselling Prevention

To ensure no two kitchens can claim the same surplus simultaneously:
1. Every match acceptance is executed in a database transaction with `FOR UPDATE` row lock on `surplus_listings`.
2. Quantity is checked: `IF available_quantity < requested_quantity THEN ROLLBACK`.
3. `available_quantity` is decreased by `accepted_quantity`, and `reserved_quantity` is increased by `accepted_quantity`.
4. Only upon dual confirmation is `reserved_quantity` cleared and `collected_quantity` incremented.
